# 正式機搬到 Oracle 的搬家計畫（f-2c，草稿）

> 狀態：**草稿，等使用者審**（2026-09-29 已補正式機唯讀盤點結果）。本文件只是計畫，任何一步正式機動作都要先問使用者。
> 對應進度頁項目：f-2（正式機搬到 Oracle 永久免費主機）。用詞照 `src/trade_alerts/catalog/fleet-glossary.json`。

- Oracle 東京已有一台永久免費 ARM 主機，**12/6 之前要完成切換**，並留至少一週緩衝。

| 項目 | 現在的正式機 | Oracle 新主機 |
|---|---|---|
| 名稱 | trading-main（GCP） | fleet-prod-tokyo |
| 規格 | e2-medium（2 vCPU／4GB，x86） | 2 核心／12GB，ARM（Ampere A1） |
| 系統 | Ubuntu（Python 3.12.3），時區 Asia/Tokyo，swap 512MB | Ubuntu 24.04（Python 3.12.3），時區目前 UTC、沒有 swap |
| 對外 IP | GCP 配的 IP | 保留 IP `161.33.186.220`（不會因重開機改變） |
| 費用 | 12/6 後付費 | 免費額度內（A1 每月 1,500 核心小時＋9,000 GB 小時＝一台 2 核心／12GB） |

## 2. 已經驗證過的事（2026-09-29）

- **ARM 能裝、測試能過**：8 個 repo 照各自 CI 指令在新主機安裝、跑測試全過（共用程式庫 381、動能 774、趨勢 522、
  加密 196、競賽 377、維運通知 143、Telegram 遙控 64、LINE 查詢 218）。
- **交易所連得到**：Binance（正式、模擬倉、測試網）與 MEXC 公開端點延遲 0.04–0.15 秒、沒被擋地區。
- **下單流程走得通**：用模擬倉金鑰從新主機掛單→用自訂編號查單→撤單（合約、現貨各一次，都沒成交）；MEXC 用只讀
  查帳戶與持倉成功。
- **固定 IP**：已換成保留 IP，交易所 IP 白名單之後綁 `161.33.186.220`。

## 3. 要搬的東西（2026-09-29 正式機唯讀盤點）

**每支策略**（動能、趨勢、加密、競賽）：

| 類別 | 位置 | 怎麼搬 |
|---|---|---|
| 程式 | `/opt/<repo>/` | **不搬**，在新主機用部署腳本從正式機分支重裝 |
| 帳本、事件日誌、匯出檔 | `/opt/<repo>/audit/` | 停機後整包複製，逐檔比對雜湊 |
| 執行狀態（持倉、安全暫停等） | `/opt/<repo>/state/` | 停機後整包複製，逐檔比對雜湊 |
| 設定與金鑰 | `/etc/<服務>/*.env` | 停機後複製，權限照舊（root:服務群組 640） |
| 真倉開關 | `/var/lib/<repo>-operations/` | 複製；新主機部署腳本預設是紙上模擬＋鎖住真實下單，要照舊機內容改回 |

**維運三件**：

| 服務 | 要搬的狀態 |
|---|---|
| 維運通知（ops-notify） | `/etc/ops-notify/ops-notify.env`、`/var/lib/ops-notify/`（已送紀錄，不搬會重送舊通知） |
| Telegram 遙控（ops-control） | `/etc/ops-control/ops-control.env`、`/var/lib/ops-control/`、`/var/lib/mexc-momentum-control/` |
| LINE 查詢（portfolio-query） | `/etc/portfolio-query/portfolio-query.env`、`/var/lib/portfolio-query/` |
| LINE 進站通道（cloudflared） | `/etc/seykota/cloudflared.yml`＋通道憑證 `/etc/seykota/<通道編號>.json`、服務 `seykota-cloudflared.service`（以 `seykota-admin` 帳號執行）、程式 `/usr/local/bin/cloudflared` |

**服務帳號與群組**：維運通知要加進四支策略的群組、Telegram 遙控要加進動能策略的群組（讀寫共用資料夾）。
部署腳本只建自己的帳號，這些跨群組設定要照舊機補。

## 4. 正式機盤點結果（2026-09-29，唯讀）

1. **服務**：跟開發機同一套——四支策略主程式、各自 5～7 個定時服務、`clock-health`、維運通知、Telegram 遙控、
   LINE 查詢，外加 LINE 進站通道 `seykota-cloudflared`。沒有失敗的服務。docker 沒在用（`/opt/containerd` 是殘留，不搬）。
2. **設定檔**：各 `.env` 的變數名稱跟開發機相同（只比名稱、沒看值）；正式機的維運通知多了趨勢策略的轉送設定，
   開發機的動能策略多兩個開發用設定，都是兩台本來就該不同的地方。
3. **資料量很小**：帳本＋狀態合計約 7.5MB（動能 7.1MB，其他都在 100KB 以下），複製幾秒內完成。
4. **四支策略都是真倉**（`STRATEGY_MODE=LIVE_ONLINE`、`DRY_RUN_ONLY=0`）。切換當天要先查各策略持倉與掛單。
5. **程式怎麼送上正式機**：正式機家目錄有 8 個 repo 的 clone（策略與維運在正式機分支、共用程式庫在預設分支），
   用 `gh` 登入的 GitHub 帳號取碼，部署腳本在正式機本機執行。新主機要有同等的 GitHub 讀取權限，二選一：
   - **建議**：一把 GitHub **細粒度唯讀權杖**（只給這 8 個 repo＋兩個交易所工具程式 repo 的讀取），存在新主機；
   - 或沿用現在的做法，在新主機用 `gh auth login` 登入你的帳號（權限比需要的大）。
6. **LINE 進站**：LINE 後台的 webhook 走 `seykota-admin.deepsoultouch.com` → Cloudflare 通道 → 本機 `127.0.0.1:8830`
   （LINE 查詢）。通道憑證跟著搬，**LINE 後台網址不用改**。但同一條通道在兩台同時執行時，Cloudflare 會把請求分給兩台，
   所以陪跑期間新主機**絕對不能**啟動通道。通道程式是手動裝的、不在任何部署腳本裡，搬家時補進 LINE 查詢的部署腳本。
7. **其他手動設定**：時區 Asia/Tokyo、swap 512MB 是手動設的；沒有 cron、防火牆（ufw）沒開。

## 5. 切換步驟

**原則**：同一時間只能有一台在交易；舊機保留到新機穩定一週才停用；每一步都先問使用者。

### 階段 A：新主機準備（不影響正式機）

1. 設 GitHub 讀取權限（第 4 段第 5 點），clone 8 個 repo（策略、維運切到正式機分支）。
2. 用各 repo 的正式機分支（operations）跑部署腳本裝好全部服務，**先不啟動**。
3. 建服務帳號與跨群組設定；裝 `cloudflared`（ARM 版）但**不啟動**通道。
4. 時區改 Asia/Tokyo、加 swap（2GB）；時鐘同步已確認正常。

### 階段 B：紙上模擬陪跑 1～2 天（不影響正式機）

1. 新主機四支策略維持部署腳本預設的**紙上模擬＋鎖住真實下單**（`DRY_RUN_ONLY=1`）。
2. 放入正式機的**只讀**用途金鑰，讓它照常抓行情、查帳戶；帳本是新主機自己的，不寫 Google 表。
3. **不啟動** Telegram 遙控（兩台同時用同一個機器人會搶訊息）、LINE 進站通道（會分走 LINE 查詢的請求）、**不啟動** LINE 查詢與維運通知的 LINE 發送（避免重複通知、吃每月額度）。
4. 比對兩台同一根 K 棒算出的進出場訊號是否一致；順便驗證正式機加密策略的 MEXC 金鑰在新主機能用。

### 階段 C：正式切換（要挑時間）

挑一個**四支策略都空手、或不在進出場時點附近**的時段（避開動能／趨勢 4 小時 K 棒收盤、競賽每日 08:10 台北）。
交易所上的停損單不受主機影響，持倉期間切換也不會失去停損保護，但會漏掉這段時間的移動停損調整。

1. 舊機：停止四支策略主程式與所有定時服務、維運通知、Telegram 遙控、LINE 查詢、LINE 進站通道；確認 `systemctl` 全部停下。
2. 舊機 → 新主機：複製第 3 段列的帳本、狀態、設定、真倉開關、維運狀態；逐檔比對雜湊。
3. 新主機：套用舊機的真倉開關；啟動服務；手動觸發一輪對帳與修復機器人，確認帳本對交易所一致、零錯誤。
4. 新主機啟動 LINE 進站通道（舊機的已先停），LINE 後台網址不用改。
5. 用 LINE 查詢、Telegram 遙控各實際操作一次；看 `systemctl --failed` 為空。
6. 舊機的服務**設成開機不啟動**，避免舊機被重開時兩台一起交易。

### 階段 D：穩定後

1. 觀察一週：每天看對帳狀態、服務失敗、通知是否正常。
2. 交易所 API 金鑰綁 IP 白名單 `161.33.186.220`（由使用者在交易所後台設定）。
3. 更新文件、記憶、登記冊裡所有「正式機＝trading-main」的地方。
4. 舊機停機（先不刪，保留硬碟到 12/6 前），確定不需要退回再刪除。

## 6. 出事怎麼退回

- 階段 A、B 出問題：舊機完全沒動，直接停掉新主機即可。
- 階段 C 之後出問題：新主機停掉全部服務 → 把新主機上**切換後新增**的帳本、狀態複製回舊機 → 舊機重新啟用服務。
  因為交易所是真相來源，就算帳本漏記，修復機器人與對帳也會標出差異。
- 舊機硬碟保留到確定不需要退回（最晚 12/6 前處理）。

## 7. 開發機怎麼辦

Oracle 免費額度只夠一台，給正式機用。開發機（trading-dev，GCP）12/6 後的選項，請使用者決定：

1. 續留 GCP、改付費（粗估每月約 35 美元，以 GCP 價格試算器為準）。
2. 換到別的便宜主機。
3. 不另外開開發機，只在本機開發（會少掉「先上開發機觀察」這一關，不建議）。

## 8. 使用者要做的事

- 審這份計畫，決定開發機去留（第 7 段）。
- 同意後，階段 B、C、D 每一步開始前再確認一次。
- 階段 D 在 Binance、MEXC 後台設 IP 白名單。
